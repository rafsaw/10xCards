Jasne. M1L3 to lekcja o **bezpiecznym uruchomieniu agenta, który zaczyna realnie działać na plikach projektu**: tworzy scaffold, odpala CLI, instaluje zależności, robi audyt i zapisuje raport.

## M1L3 — co masz zrobić teraz dla 10xCards

### 1. Pobierz paczkę lekcji

W katalogu kursu:

```bash
npx @przeprogramowani/10x-cli@latest get m1l3
```

To jest oficjalne zadanie praktyczne z lekcji. 

### 2. Wejdź do projektu 10xCards

```bash
cd C:\Users\rafal\repos\10xDevs3\10xCards
```

### 3. Upewnij się, że masz pliki z poprzednich kroków

Powinieneś mieć mniej więcej:

```text
context/
  foundation/
    prd.md
    tech-stack.md
```

M1L3 zakłada, że po M1L2 masz `tech-stack.md`, a bootstrapper używa go jako wejścia. 

### 4. Uruchom bootstrapper

W Claude Code:

```text
/10x-bootstrapper @context/foundation/tech-stack.md
```

Albo jeśli skill oczekuje krótszego path:

```text
/10x-bootstrapper @tech-stack.md
```

Sens: agent nie ma “wymyślać projektu z głowy”, tylko użyć stacku i oficjalnego startera/CLI. Lekcja mocno podkreśla zasadę: jeśli istnieje CLI, agent powinien delegować do CLI zamiast generować boilerplate z pamięci. 

### 5. Przy promptach permission używaj tej zasady

Nie klikaj automatycznie “Yes, don’t ask again”.

Moja praktyczna reguła:

```text
npm / npx / node          → zwykle Yes albo allow
git status / diff / add   → allow
git commit                → allow, jeśli jesteś OK
git push                  → ask, zawsze decyzja ręczna
curl / wget               → ask
rm -rf                    → pojedynczo bardzo ostrożnie, nigdy “always allow”
Bash(*)                   → nigdy allow
```

W lekcji przykład z `rm -rf .git` pokazuje, że jednorazowa zgoda może mieć sens, ale zgoda “zawsze pozwalaj na takie operacje” jest ryzykowna, bo później agent może dotknąć właściwego `.git` projektu. 

### 6. Po bootstrapie sprawdź raport

Szukaj pliku:

```text
context/changes/bootstrap-verification/verification.md
```

Tam powinieneś zobaczyć statusy typu:

```text
passed
warned
failed
skipped
```

Bootstrapper ma zakończyć się raportem `verification.md`, który dokumentuje wynik scaffoldingu i audytu. 

### 7. Zrób Git checkpoint

Po udanym bootstrapie:

```bash
git status
git add .
git commit -m "m1l3 bootstrap project scaffold"
git tag m1l3
```

To jest dobry moment na commit, bo lekcja wspomina, że po bootstrapie warto zainicjalizować/utrwalić historię projektu.

## Moja rekomendowana konfiguracja dla Ciebie

Dla 10xCards **nie używałbym YOLO mode na Windows host**. Użyj trybu pośredniego: część rzeczy allow, niebezpieczne rzeczy deny/ask.

W `.claude/settings.json` możesz zacząć od czegoś takiego:

```json
{
  "permissions": {
    "allow": [
      "Bash(npm *)",
      "Bash(npx *)",
      "Bash(node *)",
      "Bash(git status *)",
      "Bash(git diff *)",
      "Bash(git log *)",
      "Bash(git add *)",
      "Bash(git commit *)",
      "Read",
      "Edit",
      "Write"
    ],
    "ask": [
      "Bash(git push)",
      "Bash(git push *)",
      "Bash(curl *)",
      "Bash(wget *)"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git reset --hard *)",
      "Bash(git clean -fd *)"
    ]
  }
}
```

Lekcja rekomenduje właśnie stan pośredni: rutyna przechodzi bez pytania, destrukcyjne operacje są blokowane, a reszta wymaga decyzji.

## Jak użyć M1L3 przy następnym projekcie

### Greenfield — nowy projekt

Kolejność:

```text
/10x-shape
→ /10x-prd
→ /10x-tech-stack-selector
→ /10x-bootstrapper
→ sprawdź verification.md
→ git commit
→ git tag m1l3 albo project-bootstrap
```

### Brownfield — istniejący projekt

Nie uruchamiaj bootstrappera.

Użyj:

```text
/10x-health-check
```

Health-check sprawdza zależności, lockfile, test runner, CI/CD, konfigurację projektu i daje werdykt `healthy`, `needs-attention` albo `critical-issues`. 

Wynik zapisze się jako:

```text
context/foundation/health-check.md
```
