Q0 path-fork w /10x-tech-stack-selector: „Take recommended" (skrót do kroku E) vs „Design my own" (pełne kroki A→E). Komórki <none> w rejestrze (np. rust/web, js/desktop, js/cli) wymuszają ścieżkę custom — nie ma vetted defaulta.
Krok custom pathCo robi
A — FiltrPartycja po language_family → product_type (for:) → must-have features → avoid-list → deploy-compat
B — Quality gatesHard filter: typed · convention_based · popular_in_training · well_documented (per rodzina)
C — ReasoningNarracyjny wybór najsilniejszej karty (team, timeline, scale, feature flags) — bez scoringu
D — Alternatywy1–2 z pola alternatives_to_consider + ewentualny Socratic moment
E — Confidenceverified / first-class / best-effort — zawsze komunikowane przed bootstrapem
Szczelina (hard refusal): /10x-bootstrapper odmawia, gdy starter_id z tech-stack.md nie istnieje w starter-registry.yaml. Rejestr jest bramkarzem — nie da się „wymyślić" startera. Trzy wyjścia: 1) użyj bliskiej karty (vite/next/dotnet…), 2) dodaj realną kartę do rejestru, 3) dodaj kartę empty-<family> (przepis niżej).
Przepis: „empty starter" gdy żadna karta nie pasuje. Domyślnie rejestr nie ma pustej karty — to robisz ręcznie, raz, gdy stack jest nieobsługiwany. Cztery kroki:
  1. Dodaj kartę empty-<family> do starter-registry.yaml (minimalny scaffold, broad for:, convention_based: false, confidence: best-effort).
  2. Dopisz cwd_strategy: native-cwd w bootstrapper-config.yaml (id musi istnieć w rejestrze — walidator jest jednokierunkowy).
  3. Ustaw starter_id: empty-<family> w tech-stack.md.
  4. Odpal /10x-bootstrapper → potem framework / DB / deploy dokładasz sam.
empty-js:                       # starter-registry.yaml
  name: "Empty scaffold (bring-your-own)"
  language_family: js
  agent_friendly: { typed: false, convention_based: false,
                    popular_in_training: true, well_documented: true }
  for: [web-app, api, saas, spa, cli-tool, website]
  toolchain: { package_manager: npm }
  cmd_template: "npm init -y"   # native-cwd → {name}=.
  deployment_defaults: [self-host, azure-app-service, fly, vercel]
  bootstrapper_confidence: best-effort

empty-js: { cwd_strategy: native-cwd }   # bootstrapper-config.yaml
Opt-in z założenia: convention_based: false łamie quality gate → karta nigdy nie jest auto-rekomendowana, wchodzi tylko gdy świadomie nazwiesz „empty" (Socratic override). Zostaw komórki <none> jako <none> — wymuszają świadomy wybór zamiast cichego lądowania. Uwaga: pliki rejestru są pod .claude/skills/ — 10x get może je nadpisać, więc trzymaj zmianę w commicie.
Azure jako platforma: starter jest deploy-agnostyczny — platformę wybiera /10x-infra-research, nie rejestr. W rejestrze Azure ma tylko karta dotnet (azure-app-service); karty empty-* dorzucają azure-app-service / -container-apps / -static-web-apps / -functions do deployment_defaults. C#/.NET → Azure to droga utwardzona; TypeScript → Azure działa, ale nie jest defaultem rejestru.

⛉ Moduł 3, Lekcja 1 — kontrakt jakości (/10x-test-plan)

Co to jest: trwały, risk-first kontrakt jakości pisany zanim powstanie pierwszy test. /10x-test-plan to stateful orchestrator, nie generator one-shot. Pierwsze uruchomienie pisze context/foundation/test-plan.md (discovery PRD + roadmap + archive + skan hot-spotów → wywiad 5 pytań → synteza z obowiązkowym challenger-checkiem). Każde kolejne uruchomienie re-derywuje stan z artefaktów na dysku i prezentuje następny handoff. Lekcja = strategia i sekwencja rolloutu, nie konfiguracja (hooki, MCP, CI YAML → dalsze lekcje M3).

§ Anatomia test-plan.md

SekcjaZawartość
§2 Risk map5–7 scenariuszy awarii w kategoriach user/biznes (nie nazwy testów). Każde ryzyko ma źródło (PRD / archive / roadmap / wywiad / hot-spot dir + churn). Signal, nie knowledge — file:line / nazwy funkcji zakazane
§3 Phased rolloutTabela faz = stan orchestratora (maszyna stanów wyżej)
§4 StackTabela narzędzi; każda nazwa z checked: <data> (przykład kategorii, nie endorsement)
§5 Quality gatesLint · typecheck · unit+integration · e2e na krytycznych flow → mapują na realne kroki CI (lub required after §3 Phase N)
§6 CookbookStartuje jako placeholdery TBD — see §3 Phase N, rośnie per faza (location · naming · reference test · run command). To czyta /10x-tdd w L2
§7 Negative spaceCzego świadomie nie testujemy
Risk-first prioritization: ryzyka to scenariusze awarii ("Wylogowany user dociera do płatnej treści przez stary token"), nie "przetestuj formularz logowania". Impact × likelihood = oceny user/biznes, nie złożoność techniczna. Risk coverage to metryka — nie coverage linii.
Dual-layer mapping: classic najpierw — najtańszy test dający realny sygnał wygrywa; promocja do e2e tylko gdy nic tańszego nie pokrywa ryzyka. AI-native drugi — tylko gdzie dodaje sygnał, którego classic nie daje tanio; każdy wiersz AI-native ma linię "When NOT to use" (nie umiesz napisać → wytnij wiersz). Classic-only = plan z 2020; AI-native-only = hype.
Granice lekcji: NIE pisz kodu testów (L2 /10x-tdd) · NIE konfiguruj hooków (L3) · NIE konfiguruj MCP / Playwright / e2e / multimodal (L4) · NIE odpalaj bug→fix→regression (L5) · NIE pisz CI YAML od zera · NIE czytaj kodu po wiedzę (call graphs, schematy, "który plik ma tę awarię") — to robota /10x-research per faza rolloutu.

⛉ Moduł 3, Lekcja 2 — testy, które chronią kod (/10x-implement · /10x-tdd)

Co to jest: pisanie testów, które naprawdę chronią kod — nie maksymalizują coverage. Problem oracle i vibe-testing anti-patterns tłumaczą, czemu testy generowane przez LLM padają na realnym kodzie; lekiem jest risk-first kontrakt z L1. L1 = strategia i sekwencja (test-plan.md); L2 = kod testów dla jednej fazy rolloutu §3 naraz.

⚖ Strategia dwuwarstwowa — cost × signal

Dla każdego ryzyka: najtańszy test dający realny sygnał. Nie domyślnie e2e „bo bezpieczniej", nie pogoń za procentem coverage.

◎ Oracle & vibe-testing anti-patterns

Reguła oracle: to, co kod powinien robić, pochodzi ze źródeł (PRD, docs, tech-stack, domena) — nie z czytania implementacji. Jeśli implementacja ma bug, skopiowanie jej outputu jako wartości oczekiwanej daje mirror test, który przechodzi… przeciw bugowi. Gdy źródła nie rozstrzygają jednoznacznie — STOP i pytaj, nie zgaduj.

Mutation testing (Stryker) — selektywna bramka: coverage mówi „ta linia się wykonała"; mutation score mówi „czy test by padł, gdybym zepsuł tę linię?". Używaj po fazie ryzyka, nie jako gate na każdy commit. Dwie dźwignie jakości (one-time setup per projekt): seed (seed.spec.ts) — egzemplarz, na którym wzoruje się każdy test (what you show is what you get: getByRole w seedzie → w testach też; waitForTimeout w seedzie → dziedziczą wszystkie). E2E rules — plik reguł, który agent czyta sam przed generacją. Prompt dodaje tylko to, czego dźwignie nie kodują: ryzyko, flow, real-vs-mocked. Uwaga: API wołane server-side nie złapie page.route() — mockuj tam, gdzie serwer faktycznie woła.
Dwie granice do zapamiętania: DOM (snapshot) = default, vision (--caps=vision) tylko jako suplement na ryzyka czysto wizualne (layout, z-index, animacja); regresja pikselowa → narzędzia deterministyczne (toMatchSnapshot, Argos, Lost Pixel). Healer pomaga na selektory, szkodzi na logikę: zmieniony selektor → healer go re-finduje (przez PR review, nigdy auto-commit); zmienione zachowanie biznesowe → healer maskuje bug → to robota debugowania (L5), nie healingu.
Granice lekcji: NIE instaluj Playwrighta / nie scaffolduj configów / nie wiruj CI (skill zakłada, że są — tworzy tylko seed + rules) · NIE napędzaj ryzyk nie-browser-level (redirect tdd/implement) · NIE napędzaj feature'a, którego nie ma (STOP → implement) · failing E2E to debug (L5), nie generacja ani healing · selekcja modelu VLM / koszt → temat debugowania (L5), nie testowania.

⛉ Moduł 3, Lekcja 5 — debugowanie: test-driven bugfixing + obserwowalność (/10x-tdd · Sentry)

Co to jest: domknięcie pętli jakości M3 — co robić, gdy bug już jest (znaleziony ręcznie, przez red test E2E z L4, albo przez audyt anti-patternu). Rdzeń = test-driven bugfixing (TDB): dla znanego defektu najpierw napisz najmniejszy test, który pada z powodu buga (RED), potem minimalny diff do GREEN, potem refactor pod zielonym — a test zostaje na zawsze jako regression armor. Wehikuł lekcji w tym projekcie: audyt swallowed exceptions (catch, który łyka wyjątek bez logu i bez raportu) → seam obserwowalności → Sentry. Artefakty: foundation/swallowed-exceptions-audit.md (raport + tracker) · change observability-sentry (zarchiwizowany).

Bug jest niewidzialny dla testu z tego samego powodu, co w produkcji — brak seamu. Dlatego seam (reportError) musi istnieć zanim red-testniesz swallow, a Sentry (implementacja seamu) wchodzi ostatnie — jest enablerem testowalności, nie celem. Naprawa testowalności i naprawa obserwowalności to ten sam akt.
Strict TDD ostrzy plan — RED rodzi seam: /10x-tdd zabrania budować production code przed failing testem, więc nie ma osobnej fazy „zaprojektuj seam": RED test referuje reportError(...), pada bo moduł nie istnieje, a GREEN tworzy minimalny seam, który go satysfakcjonuje. Seam = jedno call site zamiast N inline'owych wywołań SDK — kasuje problem propagacji u źródła. Specimen wybieraj jak na L2: wyekstrahowana czysta funkcja (zero Reacta) zamiast logiki inline w komponencie (render + fetch mock + event sim).
Git archaeology — naprawiaj konwencję, nie instancję: intuicja mówi „to boilerplate ze startera" — git log -G pokazało, że nie: pattern był ręcznie napisany w jednym commicie feature'owym i rozszedł się copy-paste na 5+ komponentów w miarę wzrostu appki. Wniosek: 5 ręcznych fixów zakonserwowałoby zduplikowane parsery; ekstrakcja jednego helpera + jednego seamu to lek — pozostałe miejsca stają się refactorem pokrytym jednym testem. Łap konwencję wcześnie, bo jeden swallow napisany raz replikuje się sam.

∿ Ekonomia kontekstu przy dużej skali

Maximum Effective Context Window: okno kontekstowe to skończony budżet uwagi, nie magazyn — użyteczność spada, im więcej wrzucisz. Oficjalne „1M tokenów" jest mocno zawyżone vs okno efektywne: kierunkowo najmocniejsze modele trzymają jakość do ~250K, tańsze tracą już ok. ~100K (liczby orientacyjne, zależą od modelu i zadania). Ta sama zasada zaraz wróci przy kodzie — agent (i ty) nie wczyta całego repo na raz → progresywne ujawnianie skali w L2–L5.

Sekcje: TL;DR (+ warstwy w Mermaid) · Teren · Realne powiązania (couplingi + warstwy + cykle) · Strefy ryzyka (4–6, jedna linijka „dlaczego") · Kogo zapytać · Pierwszy dzień (5–8 plików) · Ograniczenia.

Etykieta bez dowodu to domysł. Robocze oznaczenia z dowodu, nie z nazwy folderu: core / supporting / peripheral · deep / shallow · stable / volatile / seasonal · load-bearing / contained · sensitivity high / med / low. Dla każdego wrażliwego modułu zapisuj cztery linie: evidence · inference · caution · unknowns — nie surową tabelę metryk. Coupling czytaj wielowymiarowo: incoming (Ca) · outgoing (Ce) · contract · runtime (DI, feature flagi, webhooks, codegen — niewidoczne w grafie) · co-change.
W tym projekcie (10xCards, context/map/ + architect-report §2): centrum grawitacji to infrastruktura — src/lib/supabase.ts (fan-in 16) — a NIE headline-feature „AI" (openrouter.ts to wąska szprycha, fan-in 1–2, najłatwiej wymienialna). Graf nietypowo zdrowy (0 cykli, 0 sierot, 0 naruszeń reguł); ukryty cross-cutting inwariant: account-retention.ts (fan-in 6) wpina się w każdy mutujący endpoint. Dominujące ryzyko jest wiedzowe (bus factor 1), nie strukturalne — i to retention/write-lock, nie AI, idzie do Deep Focus w L3.
