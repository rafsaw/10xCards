Sequence diagrams — Human ↔ Skills ↔ Artifacts

Read every diagram the same way: what you do → what you invoke → what delegates autonomously → what artifact returns → where automation stops for you.

Interaction legend
HUMAN ACTION — you write, choose, review or approveINVOKE — you explicitly start a skillDELEGATES — autonomous skill → skill handoffARTIFACT — durable result returns✕ HUMAN GATE — automation stops for your decision
Sequence 0 · Idea shaping / routing → downstream delivery
Memory hook: om-brainstorm shapes and routes, but it does not execute the route. After HUMAN GATE #1 it may write the brief and emit machine-readable Next: / Brief:. Then control returns to the human. HUMAN GATE #2 decides whether to actually invoke the recommended downstream skill. In Lesson 14 the observed recommendation was: Next: om-auto-create-pr "Fix stale skill-coverage facts in AGENTS.md and README and make the v16 learning map the lab's orientation surface — brief: .ai/specs/briefs/2026-08-17-lab-orientation-doc-fixes.md" with Brief: .ai/specs/briefs/2026-08-17-lab-orientation-doc-fixes.md. The PR creation step shown after Gate #2 is the next lifecycle; it was not executed in Lesson 14.
Sequence 1 · Feature path
Memory hook: human brief → invoke om-auto-write-spec → om-spec-writing creates the SPEC DOCUMENT → om-auto-write-spec continues autonomously and publishes the SPEC PR → HUMAN GATE → implementation chain.
Sequence 2 · Issue / defect path
Memory hook: om-prepare-issue prepares durable work. om-auto-fix-issue starts the autonomous bug chain: verify → root cause → fix.
Sequence 3 · PR review → runtime QA → stabilization → merge
Memory hook: review → optional runtime QA → merge-readiness automation → human ship decision → actual merge.
Sequence 4 · Runtime QA stack — shared capability
Important: om-auto-qa-pr and om-integration-tests are sibling capabilities. Both use om-prepare-test-env.
Sequence 5 · Post-merge lifecycle — sibling capabilities
Lesson 15 runtime: both skills consumed the same real merged history but answered different questions. om-auto-update-changelog produced a release-level narrative from 10 merged PRs; om-close-fixed-issues reconciled authoritative PR→Issue links and found the tracker already clean. They are siblings, not a sequence. The changelog skill delegates to om-auto-create-pr only in a real run; our dry-run intentionally stopped before mutation.
Sequence 6 · PR portfolio visibility → human-selected action
Lesson 16 runtime: the natural queue contained 0 open PRs, so the observed report returned Ready 0 / Almost Ready 0 / Blocked 0. The important boundary was still visible: om-merge-buddy scanned repository-wide PR state read-only, did not create or mutate work, treated local uncommitted skill-installation changes as out of scope, and only suggested possible downstream skills. The detailed three-way classification remains documented rather than runtime-observed.
Sequence 7 · Pipeline learning loop
Memory hook: retro reports evidence and stops. A human decides whether that evidence becomes an improvement Issue and whether to execute it. Lesson 13 runtime: 10 finished PRs examined, 9 classifiable, 7 clean single-pass, 2 unexplained second-pass, 0 hard recoveries; 0% declared-outcome coverage exposed a telemetry gap. Human-approved handoff created Issue #13, but implementation was intentionally stopped at the second human gate.
