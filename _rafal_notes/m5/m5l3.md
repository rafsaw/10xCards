## Krok 2 — requirements.md

Do pliku dajemy MVP:

```md
## Overall concept

- GitHub Actions workflow for pull requests to master
- Review is executed by our existing M5L2 code review agent
- Use composite action so the workflow stays readable

## Input parameters

- pull request title
- pull request description
- git diff

## Code Review Criteria

- implementation correctness
- idiomaticity
- complexity / maintainability
- tests and risk coverage
- security

## Parked for later

- business alignment
- architecture fit across wider system context

## Expected side-effects

- PR comment with review summary
- label: ai-cr:failed OR ai-cr:passed

## Expected behavior

- first review runs on new PR
- retry review when label ai-cr:review is added
- advisory only for now: failed AI review should not block merge yet
```

To jest zgodne z podejściem z video: najpierw luźne wymagania, potem research/plan/implement.

## Krok 4 — plan

Po researchu:

```bash
/10x-plan ci-cd-code-review Plan implementation of GitHub Actions based AI code review pipeline using current code reviewer agent and requirements.md
```

W planie pilnujemy decyzji:

```text
- advisory only, nie blokujemy merge
- labels: ai-cr:passed, ai-cr:failed, ai-cr:review
- PR comment jako dowód
- OpenRouter key jako GitHub Secret
- composite action lokalnie w repo
- workflow w .github/workflows/ai-code-review.yml
```

## Krok 5 — implementacja fazami

Nie wszystko naraz. Najbezpieczniej:

```text
Phase 1: dopasowanie agenta do PR inputów
Phase 2: composite action
Phase 3: GitHub workflow
Phase 4: testowy PR + screenshots
Phase 5: promptfoo evals
```

Na zaliczenie 10xChampion najważniejsze są fazy 1–4. Promptfoo jest ważne do M5L3, ale dowód Champion domyka pipeline na PR. Lekcja mówi, że pipeline domyka się właśnie w M5L3 i wtedy zbierasz screenshots. 

Pierwszy ruch teraz: zrób branch i `requirements.md`, potem pokaż mi zawartość albo wynik `10x-new`, i przejdziemy do research promptu.


Dobrze, że to zauważyłeś. 👍 I to jest dokładnie ten krok z filmu, o którym zapomniałem.

Między **requirements.md** a **10x-research** autor robi jeszcze **doprecyzowanie kryteriów z agentem**.

Na screenie jest dokładnie ten prompt:

```text
'context/changes/ci-cd-code-review/requirements.md'
please extend code review criteria
by adding one sentence of clarification or description,
also 1 to 10 grading,
explaining both sides of the spectrum
```

To nie jest jeszcze research.

To jest po prostu **ulepszenie requirements.md**, żeby zamiast:

```text
Implementation correctness
```

mieć np.:

```text
Implementation correctness

1 = logic is broken, missing edge cases, introduces regressions

10 = implementation is fully correct, handles edge cases, integrates cleanly with existing design
```

I tak dla każdego kryterium.

## Czy warto to zrobić?

Moim zdaniem **tak**, z dwóch powodów:

1. Jest to dokładnie workflow pokazany w filmie. 
2. Potem agent wykorzysta te definicje do wygenerowania Zod schema i structured output.

Czyli flow powinien wyglądać tak:

```text
1. requirements.md
        ↓
2. Agent rozszerza kryteria (to co masz na screenie)
        ↓
3. /10x-research
        ↓
4. /10x-plan
        ↓
5. implement
```

---

## Ja zrobiłbym jedną małą zmianę

Nie pisałbym dokładnie tego samego promptu.

Dałbym trochę bardziej precyzyjny:

```text
'@context/changes/ci-cd-code-review/requirements.md'

Please extend the Code Review Criteria section.

For each criterion:
- add a short description,
- define what score 1 means,
- define what score 10 means.

Do not change the overall intent of the document.
Keep everything concise and suitable for use as AI review criteria.
```

To daje agentowi mniej swobody do zmiany całego dokumentu, a dokładnie robi to, czego oczekujemy.
